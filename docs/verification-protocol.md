# 协议 401 数据传输与校验机制说明

本文档面向开发者，说明协议版本 **401**（`4.0.1-preview`）的数据块校验、传输后全文件 SHA-256 校验、批量重传修复以及 Android 跨进程文件句柄的生命周期设计。

`HybridFileXfer-PC` 与 `HybridFileXfer-Android` 共享 `core`、`nio` 和 `security` 三个包的代码，`tools/build_desktop.py --test` 会在构建时校验两端共享源码是否完全一致。协议 401 在握手阶段会拒绝协议 400 及更早版本的客户端。

---

## 一、数据传输阶段与 CRC32 分块校验

1. **发送帧与确认帧格式**
   - 每个数据块直接基于发送端的 1 MiB 堆内存缓冲区计算有效载荷的 CRC32，无需额外拷贝或二次读盘。
   - 发送端一次性写入 24 字节块头：`command (2B) + fileId (4B) + offset (8B) + length (4B) + crc32 (4B)`（外加帧协议开销），紧接着发送数据块内容。
   - 接收端在收到数据块后先校验 CRC32，校验通过后才写入 `.part` 暂存文件、更新检查点并推进已确认前缀。
   - 正常确认帧（ACK）合并为单次 30 字节响应（含空错误字符串长度 0），在不增加网络往返（RTT）的前提下完成分块确认。

2. **分块重传与故障通道降级**
   - 若接收端检测到 CRC32 不匹配，会返回携带校验错误状态的负确认帧（NACK），发送端将该数据块重新放回共享调度队列重试。
   - 若某条数据通道连续出现校验失败或 I/O 异常，发送端会关闭并剔除该故障通道，其未确认的数据块由其余健康通道继续发送；磁盘满、无权限等明确存储错误则会直接作为文件失败上报，不会无休止重试。
   - 每个文件结束或重试中止时都有明确的帧边界标记，防止后续控制指令误读残留的数据块帧。

3. **默认提交流程（未开启全文件 SHA-256 时）**
   - 全文件 SHA-256 校验默认关闭。在此模式下，文件所有分块接收并通过 CRC32 校验后即按接收端设定的同名文件冲突策略（保留两份、跳过、覆盖）原子提交为目标文件。
   - 断点续传在复用已有 `.part` 文件前仍会读取并核对已持久化的前缀哈希；若用户显式开启“内容一致时跳过（增量传输）”，传输前也会计算完整内容哈希以决定是否跳过同名文件。

## 二、延后全文件 SHA-256 校验与批量重传修复

当手机端或电脑端任意一方勾选“传输后完整 SHA-256 校验”时，会话对本次任务启用双端全文件校验流程：

1. **暂存封存与目标占坑（Claim / Lease）**
   - 数据阶段接收完一个文件后，接收端将其暂存文件封存（Seal）并关闭写入句柄，仅在内存中保留轻量级描述符、会话租约（Session Lease）及目标路径占坑记录（Target Claim），避免在海量文件传输时耗尽系统文件描述符（FD）。
   - 占坑记录用于在释放文件锁等待最终校验的窗口期内，防止其他并发会话或不同源文件意外覆写同一目标路径。

2. **双端并发哈希与控制通道轮询**
   - 初始数据传输阶段全部完成后，发送端与接收端各自启动 2 个工作线程，在最多 8 个文件的滑动窗口内并发计算 SHA-256。
   - 仅传输发起方（Owner）负责读写控制通道，通过非阻塞轮询消息（Poll）交换双方已计算完成的哈希结果与软停止标志，不在控制通道处理函数内同步阻塞等待大文件哈希计算。
   - 单个文件必须等到两端哈希均计算完毕并完成比对（或发生明确的文件读写错误）后，才会归入“已校验”计数。

3. **比对提交与多轮批量修复**
   - **摘要一致**：接收端将该文件的封存暂存代际（Generation）正式发布为目标文件。
   - **摘要不一致**：记为校验不匹配（Mismatch）。若在读取源文件、校验文件元信息或发布目标文件时发生磁盘/权限错误，则直接记为该文件失败。
   - **批量重传**：当前轮次所有待校验文件比对完毕后，所有摘要不匹配的文件会作为同一批次重新传输，并在重传完成后进入下一轮 SHA-256 校验。
   - **代际保护**：重传文件沿用首轮确定的目标路径（“保留两份”策略不会在每轮重试时重复递增后缀编号）。重传数据会写入新的暂存代际，在新的重传副本完整接收前保留上一轮已完整收到的暂存文件，确保用户在重传中途点击停止时不会丢失上一轮已收到的完整数据。
   - **统计口径**：界面实时进度展示当前轮次的校验进度；最终传输摘要（`TransferSummary`）则按去重后的独立文件数统计“校验通过、校验失败、未校验、重发文件数”。

## 三、停止校验（软停止）与取消传输（硬取消）

- **停止校验与重试（Soft Stop）**：从进入首轮 SHA-256 校验起直至后续修复轮次均可触发。两端通过最终握手同步停止标志并保持当前网络连接可用：
  - 已完整接收但尚未完成 SHA-256 比对的文件（未校验文件）会被保留并发布为正式文件；若目标路径已有同名旧文件，即使冲突策略设为“覆盖”，也会将未校验文件另存为新副本，避免用未完成校验的数据覆盖用户原有文件。
  - 已明确判定为 SHA-256 不匹配的文件会保留在暂存区供排查，不会发布为正式文件；中途被打断的半截重传副本则会直接丢弃。
- **取消传输（Hard Cancel）**：在数据传输阶段点击取消，或发生连接断开、工作线程无法响应停止时，直接关闭当前连接并中断阻塞 I/O。

## 四、Android 跨进程文件描述符（Binder FD）管理

在 Android 端，实际文件系统读写由独立进程（`:IOService` 或 `libsu` 托管的 `RootIOService`）执行：

- **零内容拷贝传递**：文件内容不经过 Binder RPC 传输，跨进程接口仅传递 `ParcelFileDescriptor` 与轻量控制参数。
- **句柄代际（Epoch）与关闭确认**：客户端使用 `TransferHandleRegistry` 维护当前任务的句柄代际（Epoch）。每次打开远程读写描述符都会在服务端登记占坑，直到客户端显式关闭本地 `ParcelFileDescriptor` 并发送关闭确认后，服务端才释放对应的文件锁。
- **非阻塞取消与后台清理**：主线程或 UI 触发取消时，仅在内存中立即可见地推进代际号（拒绝任何迟到的异步打开结果），并将可能阻塞的句柄关闭与远端清理任务交由独立后台线程执行；在上一轮清理完成前不会启动新的传输任务，从而避免跨进程句柄竞态。
